## Context

The first CLI command (DL-034) builds a sync map (DL-003) ahead of time, so a site can serve a small JSON file to `<segno-player sync="…">` instead of the position files and the SVG text that the player otherwise fetches and parses. The core already does the work (`buildSync`, `readViewBox`). The command has to find the files, report mistakes clearly, and fit into a site's build scripts.

A MuseScore job (see the README) writes `song.mpos`, `song.spos` and the pages as `song-1.svg`, `song-2.svg`, …, numbered from 1 even for a single page. A shell glob such as `song-*.svg` sorts `song-10.svg` before `song-2.svg`, so it can't be relied on for page order.

## Decision

`segno build-sync [<name>] [options]`:

- `<name>` is the export's path without an extension, for example `public/scores/song` (a trailing `.mpos` is accepted and stripped). From it the command takes `<name>.mpos` (required), `<name>.spos` (used when it exists) and the pages `<name>-1.svg`, `<name>-2.svg`, …, counting up to the first missing number.
- Options override what the name gives: `--positions <file>`, `--notes <file>`, `--no-notes`, `--page <file>` (repeatable, in page order) and `-o, --out <file>`. Without `<name>`, `--positions`, at least one `--page` and `--out` are required.
- The map is written to `<name>.sync.json` by default, overwriting it, or to stdout with `-o -`. It is compact JSON with a trailing newline. A one-line summary goes to stderr: the output path, the number of pages, bars, bar events and notes, and the size.
- A build step is strict. A `.spos` that is missing when given with `--notes`, or that doesn't fit the pages, fails the command with a hint to pass `--no-notes`. It does not fall back to a bars-only map, as the browser does (DL-017).
- Errors name the file involved and print the core's message. For errors from `buildSync` or `readViewBox`, a short hint follows, listing the export settings that make the positions and pages disagree (one job, one MuseScore version, the default PNG resolution) and linking the README's export section. The bars are built first and the notes second, so a failure names the `.mpos` or the `.spos`. The hint is chosen by which step failed, not by parsing the message text. The files are read one at a time, positions first, then notes, then pages, so the problem reported is always the first in that order: a mistyped name reports its missing `.mpos`. Only when the `.mpos` is there but no pages are found is the hint to give them with `--page`. An empty name is a usage error.
- Exit codes: 0 on success, 1 when a file can't be read or the map can't be built, 2 for a usage error.

## Rationale

- Using MuseScore's own naming lets the usual case be one argument, `segno build-sync song`, while the flags cover renamed or relocated files.
- Counting pages up from 1 instead of globbing keeps page order right past page 9, and needs no glob dependency.
- Failing on a bad `.spos` keeps a broken note cursor from being shipped unnoticed. In the browser, playing on without it is the better outcome for a listener. At build time the publisher is there to fix it.
- Not matching on the core's message text keeps the core's messages free to change.
- Compact output keeps the file at its intended size (about 2 KB per song), and a stdout option lets a build pipe it wherever it wants.

## Consequences

- The README replaces "coming" with a short section on prebuilding, and the CLI's `--help` documents the options.
- The command has no `unitsPerSvgUnit` option. A non-default PNG resolution is treated as an export mistake, as in the player (DL-002), and can be added later if a real need appears.
- The command doesn't check the audio's length against the last event (the "Play repeats" check). That needs MP3 parsing in Node, so the player keeps doing it at play time.
