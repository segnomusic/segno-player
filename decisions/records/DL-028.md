## Context

Sites already declare their language using HTML `lang`. Requiring a separate player locale would duplicate this information and make a Swedish page accidentally retain English controls.

## Decision

Use the standard HTML `lang` attribute and its existing DOM property as the public language API. An explicit player language takes priority; otherwise use the inherited HTML language from ancestors, including shadow hosts and the document element. Match regional tags such as `sv-SE` to `sv`, case-insensitively. Unsupported, explicitly empty or unspecified languages use the complete English catalog. Do not infer language from browser preferences and do not add a separate locale property, selector or language-change event.

React to changes of the player language and inherited ancestor language while connected, and resolve again after reconnection, state-preserving moves or document adoption. Observe relevant ancestor language attributes rather than all mutations throughout the document, and disconnect observers when the player is disconnected. Mark internal translated regions with the resolved catalog language so English fallback text is announced as English without overwriting the author-supplied player `lang`.

Use the native `:lang(sv)` match to resolve the supported Swedish language range; the browser supplies inheritance, regional-tag matching, case insensitivity and explicit-empty behavior. Everything else uses the English catalog.

## Rationale

Standard HTML language inheritance keeps the player aligned with its host site and gives authors the usual per-element override. Deterministic English fallback avoids mixing dictionaries and does not depend on the device running the page.

## Consequences

Language resolution depends on DOM context but catalog data remains DOM-free. Browser tests cover document and local inheritance, regional and case variants, empty and unsupported overrides, changes, moves, cleanup and independent players.
