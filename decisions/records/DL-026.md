## Context

The first release of `@segnomusic/player` should be `0.1.0`, reviewed through pull requests. The existing release workflow can create version changes, but GitHub organization policy currently prevents its PR from opening. Its publish job also lacks Chromium for the browser suite, and Changesets does not update the npm lockfile by itself. The package does not yet exist on npm, and the maintainer chose a local interactive first publish rather than storing a bootstrap token in GitHub.

## Decision

Keep the Changesets version-PR and GitHub-hosted OIDC publish model of DL-012. Add main-only manual dispatch for retrying releases. Validate both version candidates and published releases with the full checks, install Chromium in the jobs that run browser tests, and smoke-test an actual packed tarball installed in a clean temporary consumer. Versioning updates the npm lockfile before validation. Build during packing so a local publish cannot accidentally ship stale compiled files.

The GitHub `npm` environment permits branch `main` only. Release builds do not restore a package-manager cache. The organization and repository must allow Actions to create version PRs while default token permissions stay read-only; the workflow does not approve or merge its PRs.

Bootstrap `@segnomusic/player@0.1.0` with a local npm login after merging its release PR, explicitly disabling provenance only for that local publish because it cannot issue GitHub OIDC attestations. No npm publishing token is stored in GitHub. Configure the npm trusted publisher for organization `segnomusic`, repository `segno-player`, workflow `release.yml`, and environment `npm`, allowing direct npm publishing; later releases use OIDC and provenance. Include one-time first-publish, GitHub release/tag, and verification steps in the release handoff, not `CONTRIBUTING.md`.

## Rationale

Testing the installed tarball catches missing files and export mistakes that repository self-imports miss. Keeping version and lockfile metadata synchronized makes release commits reproducible. A local bootstrap avoids a long-lived write token; its provenance limitation is explicit rather than silently weakening subsequent releases. Manual dispatch permits retries without dummy commits and remains restricted to main.

## Consequences

- `0.1.0` needs an interactive npm account with publishing access to the segnomusic scope; the release workflow cannot bootstrap it without a configured publisher.
- The local bootstrap release has no provenance attestation. Subsequent CI releases retain `publishConfig.provenance: true`.
- Bot-created PRs may not trigger ordinary PR workflows with GITHUB_TOKEN, so the version script validates its candidate before creating or updating the PR.
- Release rehearsal exposed timing-dependent canvas coverage close to the existing 90% floor; a deterministic raster-context failure test covers the error path without changing production behavior or lowering the threshold.
- The unscoped `segno` CLI is deferred to a separate repository and is not published as a name-reservation placeholder.
