## Context

The spike rebuilt its visible canvas and tile objects on every animation frame, used one fixed-size single-page raster, and ran a second playback loop. That is unsuitable for long scores and mobile devices. The official player already has the required media lifecycle, timeline leads, repeat handling, cancellation, and fallback behavior.

## Decision

Canvas rendering is divided into pure layout calculations and a page-aware canvas view. The layout module derives systems, bar groups, stable crops, reflow rows, coordinate projections, and hit-testing without DOM or audio access. The canvas view owns resizing, SVG decoding, and a lazy per-page raster cache with resolution and memory limits.

`SegnoPlayer` remains the sole media and timeline orchestrator. Static score pixels redraw only when the source, mode, window, grouping, page, container size, or pixel density changes. Existing DOM bar and note overlays move above the canvas through layout projections; only those lightweight overlays update during ordinary playback frames. Full score remains the fallback when sync or canvas assets are unavailable.

Canvas SVG assets load on demand, including with prebuilt or property-provided sync maps. Mode changes preserve media time, playback state, tempo, and timeline state. Canvas loading does not block audio or change the established `canplay` contract.

## Rationale

Separating geometry from rendering makes the spike mathematics testable and prevents DOM and media coupling. Static score rendering plus DOM overlays avoids repeated raster resampling and backing-store resets while preserving theming and reduced-motion behavior. Lazy bounded rasters make memory use predictable and support multi-page scores.

## Consequences

- DL-017 retains one playback loop and its paused seek updates, extended to drive the active score view.
- Full-score users do not pay the canvas asset-loading cost.
- Raster failure degrades to full pages and audio rather than preventing playback.
- Canvas views must release observers, stale loads, and replaced raster resources.
- Layout, browser integration, visual alignment, and memory-sensitive behavior require focused tests.
- The player size budget rises from 12,000 to 24,000 bytes gzipped for the added layout, raster, mode, and control code and subsequent player work; the dependency-free ESM build remains unchanged.
